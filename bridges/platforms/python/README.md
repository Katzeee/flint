# Python platform

This platform provides the native Bridge binding, request pump, Python execution components, and Qt connection controls for host integration authors. Installation and application-specific behavior belong to the [host guides](../../README.md).

A host composes a fixed [BridgeManager](src/flint_bridge/connection/bridge_manager.py) from its registration identity, an execution-runner factory, and an initialization dispatcher. Importing that integration does not create a connection or touch the application's UI. The factory runs when a new Bridge needs an execution context; reusing or configuring an existing Bridge retains its runner. The factory owns cleanup if it fails before returning the runner. The host decides which executor and thread strategy to compose. [CodeRunner](src/flint_bridge/execution/runner.py) combines a Python executor with a strategy, while Blender's timer strategy belongs to the Blender integration.

The initialization dispatcher accepts a callback from the attach worker and invokes it once on the thread required to establish the Bridge. A standalone host can invoke it directly; an integration using an event loop must initialize that loop before accepting work. Attach waits for initialization and registration within one timeout budget, so an integration that queues work onto the main thread must call attach from a worker. A timeout cancels initialization that has not started. If initialization has started, the caller receives an uncertain outcome and the operation may still complete. Registration timeout leaves the established Bridge available for inspection and reconnection. In-process startup can call connect directly on the required thread.

BridgeManager reuses a matching Bridge within the interpreter, serializes connection changes, and closes a newly created runner if startup fails. [Bridge](src/flint_bridge/connection/bridge.py) owns the runner, request pump, and native core, and releases the core if its thread cannot start. A settings change retains the active runner. Disconnect follows the shared [core lifetime and resource release contract](../../../docs/contributing.md#ownership); a false return requires another disconnect after execution finishes. A host integration cannot replace or disconnect a different host's active Bridge. The native core separately enforces the process claim across runtimes and owns connection state, validation, reconnection, and status snapshots. [NativeCore](src/flint_bridge/connection/native_core.py) translates its C ABI and errors.

The Python executor retains its namespace across requests and captures output from the execution thread. Host adapters own dispatch and unloading; closing a strategy cancels queued work without forcibly terminating running host code. Custom strategies can use the platform's [Invocation](src/flint_bridge/execution/strategies/invocation.py) to coordinate waiting, results, and cancellation across threads.

Qt execution and connection controls share the platform's [binding resolver](src/flint_bridge/qt.py). It reuses the binding with a running application; the host owns any fallback needed before Python has imported that binding. Qt dispatch belongs to the [Qt strategy module](src/flint_bridge/execution/strategies/qt.py), while application checks, native window wrapping, and host-specific dispatch remain with the host. Refer to the implementation for exact APIs, defaults, and error types, and to the repository [development guide](../../../docs/contributing.md) for building and testing.
