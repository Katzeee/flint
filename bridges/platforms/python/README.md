# Python platform

This platform provides the native Bridge binding, Python execution capabilities, and Qt connection controls for host integration authors. Installation and application-specific behavior belong to the [host guides](../../README.md).

A host composes a fixed [BridgeManager](src/flint_bridge/connection/bridge_manager.py) from its registration identity, a factory of [execution capabilities](src/flint_bridge/execution/capabilities.py), and an initialization dispatcher. Importing an integration does not create a connection or touch the application's UI. The factory runs when a Bridge is created and returns an executor and a scheduler; reusing or configuring an existing Bridge retains them. A Bridge that cannot be created closes the scheduler it was given.

The native core orchestrates every execution: it prepares, runs, cancels, or discards it, combines output, and reports the result. The executor's `run(prepared, out, err)` executes code, and an optional `prepare(request)` produces the value it runs, which defaults to the request. Either may return a value, raise, or return a `concurrent.futures.Future` that completes later from any thread. A failure is reported as `preparation_failed` or `execution_failed` with its traceback. Output written to `out` and `err` streams to the core until that call completes; later writes are ignored. [CodeExecutor](src/flint_bridge/execution/executor.py) compiles Python during preparation, retains its namespace across requests, and captures output from the execution thread while running code.

The scheduler's `post(callback)` must run each callback once on the thread where the host executes code, and `close()` ends it after the Bridge is released. The core posts from its own dispatcher thread, never the network thread, and prepares and runs code inside those callbacks. The [Python binding](src/flint_bridge/connection/execution_binding.py) only translates these calls; it keeps no queue or stage of its own. [Scheduling](src/flint_bridge/execution/scheduling.py) provides a dedicated worker thread, a queue drained by a host loop, and Qt main-thread posting. Blender drains a queue from its timer. The callback contract lives in the [native header](../../../crates/flint-bridge-core/include/flint_bridge_core.h).

The initialization dispatcher accepts a callback from the attach worker and invokes it once on the thread required to establish the Bridge. A standalone host can invoke it directly; an integration using an event loop must initialize that loop before accepting work. Attach waits for initialization and registration within one timeout budget, so an integration that queues work onto the main thread must call attach from a worker. A timeout cancels initialization that has not started. If initialization has started, the caller receives an uncertain outcome and the operation may still complete. Registration timeout leaves the established Bridge available for inspection and reconnection. In-process startup can call connect directly on the required thread.

BridgeManager reuses a matching Bridge within the interpreter and serializes connection changes. Disconnect follows the shared [core lifetime and resource release contract](../../../docs/contributing.md#ownership): the core cancels execution whose code has not started and discards its prepared value, while started preparation or execution finishes first. A false return requires another disconnect after it finishes. Host code is never forcibly terminated. A host integration cannot replace or disconnect a different host's active Bridge. The native core separately enforces the process claim across runtimes and owns connection state, validation, reconnection, and status snapshots. [NativeCore](src/flint_bridge/connection/native_core.py) translates its C ABI and errors.

Qt execution and connection controls share the platform's [binding resolver](src/flint_bridge/qt.py). It reuses the binding with a running application; the host owns any fallback needed before Python has imported that binding. Application checks, native window wrapping, and host-specific dispatch remain with the host. Refer to the implementation for exact APIs, defaults, and error types, and to the repository [development guide](../../../docs/contributing.md) for building and testing.
